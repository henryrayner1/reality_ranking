# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Frontend (repo root):
- `npm run dev` — Vite dev server on port 5173, proxies `/api` to `http://localhost:4000` (see `vite.config.ts`)
- `npm run build` — `tsc -b && vite build`, then copies `dist/index.html` to `dist/404.html` (GitHub Pages SPA-fallback trick; production base path is `/reality_ranking/`, dev stays at `/`)
- `npm run lint` — ESLint

Backend (`backend/`):
- `npm run dev` — `tsx watch src/server.ts`; port comes from `.env` (`PORT`, defaults to 4000)
- `npm run build` / `npm start` — compile then run compiled JS
- `npm run prisma:generate` / `npm run prisma:migrate` — regenerate client / apply schema changes
- `npm run seed` — `tsx prisma/seed.ts`

Run both together from the root: `npm start` (runs `dev:frontend` and `dev:backend` in parallel via `npm-run-all`).

There is no test suite in either package.

`backend/.env` (`DATABASE_URL`/`DIRECT_DATABASE_URL`) points at a real, already-populated Postgres instance in normal development — check it before assuming you need the `docker-compose.yml` Postgres container, which is not what's actually wired up by default.

## Architecture

- Two-package layout: Vite/React/TypeScript frontend at the repo root, Express/Prisma backend in `backend/`. No shared package — types are duplicated by hand between `src/utils/Constants.ts` and the backend's Prisma schema/route response shapes.
- Data model (`backend/prisma/schema.prisma`): `Show` → `Season` → (`Contestant`, `Episode`); `Episode` → `Elimination` / `Ranking`. A `Contestant` can have at most one `Elimination` (`Elimination.contestantId` is `@unique`).
- No auth middleware or token: `POST /api/users/login` just returns the user row, and the client keeps it in the Redux `user` slice (persisted to localStorage manually and deliberately kept *out* of redux-persist — see the comment in `src/redux/store.ts` explaining the two-competing-copies bug that caused). Admin-only UI is gated purely by a client-side `accountType` check.
- Redux (`src/redux/`) now holds only the `user` slice — `shows`/`seasons`/`episodes`/rankings all moved to React Query (`src/hooks/queries.ts`) as the single source of truth for server data, since the old Redux-vs-React-Query split let Admin edits silently go stale on the Ranking/Insights pages until a hard reload. `GET /api/shows/` returns the *entire* nested tree in one call (every show → its seasons → each season's `contestants[]` and `episodes[]`, each episode's `eliminations[]`) — every hook in `queries.ts` (`useShows`, `useSeasons`, `useEpisodesByShow`, `useShowTree`) derives from that single `['shows']` query rather than hitting separate endpoints, and every mutation across `Admin*.tsx` invalidates just `['shows']`. **Gotcha:** `GET /api/shows/:showId` (used nowhere anymore, but easy to reach for) returns a much sparser `Show` — its `seasons[]` omit `contestants` entirely — so a hook built against that endpoint will silently produce `season.contestants === undefined` instead of an empty array, crashing anything that does `.contestants.length`. Don't add a new hook against `/api/shows/:showId` without checking its response shape first. `QueryClient` (`src/main.tsx`) is configured with `staleTime: Infinity`/`gcTime: Infinity`/no background refetch to mirror Redux's old "fetch once, update only via explicit action" model — data only changes via a mutation's `invalidateQueries`.
- A page that derives "current season" from a `useState` selected-id plus a `useEffect` that resets it when the show changes (e.g. `Insights.tsx`'s old `selectedSeasonId`) will render one frame with the *previous* show's season id after the show itself has already updated — `useEffect` only runs after commit/paint, so that stale id briefly finds nothing in the new show's `seasons[]`. If a child component treats "no current season" as its own independent loading signal (e.g. `InsightsRankingTable`/`ContestantDetailPanel`'s `if (loadingFlag || !currSeason)` check), that frame shows a loading-circle flash even though every query involved is already fully cached (`staleTime: Infinity`) and nothing is actually loading. Fix by deriving the fallback season directly in the render body (same "current season, else last season" logic the effect uses) instead of only setting it via the effect — the effect can still exist to persist the choice into state for controls like `SeasonSelect`, but the *derived* value used for rendering should never depend on that state having caught up yet.
- The "currently selected show" is a URL param, not client state: `/ranking/:showSlug`, `/insights/:showSlug`, `/admin/:showSlug`, where the slug is `slugifyShowName(show.name)` (`src/utils/slug.ts`) — not the show's id, so URLs read as `/ranking/rupauls-drag-race` rather than a cuid. There's no persisted `slug` column; it's derived from `name` on every read, so **two shows with the same name would collide** (fine at this app's scale, but worth knowing if that ever changes — would need a real stored/unique slug field). Every page resolves `showSlug` back to a real `Show.id` via `shows.find(s => slugifyShowName(s.name) === showSlug)` before handing that id to the data hooks (`useShowTree(showId)` etc. still take the real id, unchanged) — don't skip that resolution step when adding a new show-scoped route or `navigate()` call, or you'll end up passing a slug where an id is expected. There is no `DefaultShowRedirect` component (removed at some point; don't reach for it) — a bare `/ranking` or `/insights` (no slug) just renders that page with `showId` undefined, showing its own "Please select a show"/"select a show" placeholder until the user picks one from `ShowSelect`, which then `navigate()`s to the slugged URL. Admin is a single page (no tabs/sidebar), routed as `/admin`, `/admin/:showSlug` and `/admin/:showSlug/:seasonNumber`: `AdminShows` is the show picker bar (dropdown + "+ New show" modal + ranking-mode toggle + delete), `AdminSeasons` the season picker bar (same shape, plus the DAILY premiere date), and once both resolve, `AdminContestants`/`AdminEpisodes`/`AdminEliminations` all render stacked below, each taking explicit `showId` + `seasonId` props and scoped to only that season (none of them has its own show/season dropdown any more). The picker bars `navigate()` themselves; `Admin.tsx` only resolves the URL. The selected season is derived in `Admin.tsx`'s render body — URL `seasonNumber` match, else the show's current season, else its highest-numbered one — so `/admin/:showSlug` with no season (and a stale/nonexistent season number) silently lands on the current season rather than redirecting. A bare `/admin` just shows the show picker and a "Select or add a show" empty state. The three editors are keyed by `seasonId` so switching seasons resets their in-progress form state. `ShowSelect` itself is still id-based internally (`shows`, `currShowId`, `onSelectShow(showId)`) — each page's `onSelectShow` looks the clicked id back up in `shows` and slugifies before calling `navigate()`.
- Two ranking modes per show (`Show.rankingMode`: `EPISODE` | `DAILY`). `EPISODE` shows open ranking a fixed duration after `airDate`. `DAILY` shows (e.g. Big Brother) open ranking per America/New_York calendar day instead of per-episode; that timezone/day-boundary math lives in `src/utils/episodeRankability.ts` and is **duplicated by hand** in `backend/src/utils/episodeRankability.ts` and `backend/src/utils/dailyEpisode.ts` (which auto-creates each day's Episode row) — keep both sides in sync, per the comments in each file.
- `ensureTodaysDailyEpisode` (`backend/src/utils/dailyEpisode.ts`) backfills every missing calendar day between a DAILY season's `premiereDate` and today, not just today — walking via `nextDayKey` (pure Y/M/D string arithmetic, deliberately not the timezone-aware `dayKeyToAirDate`/`getZonedMidnightMs` machinery, to avoid DST-drift when incrementing repeatedly) and diffing against existing rows. Only the row for *today itself* is a live/on-time creation (`Episode.isBackfilled: false`); every other row it creates for a gap (e.g. the server was down across a stretch of real days, or the poller in `dailyEpisodeScheduler.ts` wasn't running) is flagged `isBackfilled: true` — it never had a real live ranking window. It also unconditionally re-numbers *every* `Episode` in the season by `dayKey` ascending on every call (idempotent, cheap at this app's scale) so `episodeNumber`/the displayed "Day N" always matches true chronological order — meaning an existing episode's `episodeNumber` can shift after a backfill run fills in earlier gaps (safe: `Ranking`/`Elimination` relate via `episodeId`, never `episodeNumber`). `isBackfilled` is enforced server-side, not just hidden in the UI: `POST /api/rankings/create` and `/createMany` (`backend/src/routes/rankings.ts`) both reject a ranking submission for a backfilled episode with 403, in addition to the existing `isRankableNow` open-window check — the two checks are intentionally separate (`isRankableNow`/`isDailyRankable` still just means "has this day arrived", unchanged). On the frontend, a backfilled episode renders as a locked column instead of the normal active/placeholder `EpisodeComponent`: `RankingComponent2.tsx` branches (checked after `checkPastRankings`, before the normal dispatch) on `episode.isBackfilled` **or** `isMissedDailyDay` to `lockedEpisodeElements`. `isMissedDailyDay` is a second, related-but-distinct DAILY-only lock: once a newer day has opened, an earlier real (non-backfilled) day the current user never submitted a ranking for also becomes locked — only the single most-recently-opened rankable day (`latestRankableEpisodeId`, the last entry of the already-sorted `rankableEpisodes`) stays first-submittable; this is a UI-only restriction (unlike `isBackfilled`, there's no server-side rejection for a "missed" day — the ranking-open check still just verifies `isRankableNow`, so a direct API call could still submit one). `lockedEpisodeElements` doesn't invent placeholder content for either case: since no real `Ranking` can exist yet, it builds a synthetic `Ranking` from `getLastRankingNames(episodeNumber)` (the same "most recent past submission, else default roster order" lookup used to seed a freshly-activated episode) and feeds it through the existing `buildPastRankingColumn` (`src/utils/util.ts`) — so the locked column visually carries forward whatever order the last real ranking left off at, rather than showing an unrelated alphabetical roster. `InsightsRankingTable.tsx`'s `episodeColumns` does the analogous thing for `episode.isBackfilled` entries: walks `sortedEpisodes` in chronological order tracking `lastRealOrder` (the previous real day's resolved column, falling back to alphabetical only if there's no real day yet) and carries that into the backfilled day's column instead of computing rank from `contestantAverages` (always empty there). Neither blanket-grayscales the whole column (an earlier version did, via a since-removed `ContestantIcon` `locked` prop — it made eliminated and still-active contestants indistinguishable within a locked column): a locked/backfilled cell's real elimination status still drives `isEliminated` (same grayscale as everywhere else), and only the non-eliminated ones additionally get `dimmed` (`ContestantIcon`'s existing `opacity: 0.25` prop, otherwise used by `ContestantSelect`'s highlight-one-contestant feature) to signal "not an actual submission" without losing the eliminated/active distinction. `GET /api/rankings/insights/:seasonId` merges in every `isBackfilled: true` episode with empty `contestantAverages` so these columns show up there too — deliberately *not* extended to ordinary non-backfilled zero-ranking episodes (which still stay omitted as before) and *not* applying the `isMissedDailyDay` per-viewer lock at all, since Insights is aggregate/not scoped to one user's submission status. A one-off `backend/scripts/backfillDailyEpisodes.ts` (`npm run backfill:daily`) just calls `ensureTodaysDailyEpisodesForAllShows` once and logs what changed — safe to re-run any time, e.g. after extended downtime.
- `Season.endDate` (nullable timestamp — date *and* time, set from the Admin season bar's `datetime-local` "Ends" field in the admin's local time zone) ends a season: (1) `ensureTodaysDailyEpisode` caps day-row creation at the Eastern calendar day `endDate` falls on (its `season` param requires `endDate` in the type so a new call site can't silently forget it — every `select` feeding it must include `endDate: true`); (2) `POST /api/episodes/create` rejects (400) an `airDate` after `endDate`, or any new episode once ended; (3) `POST /api/rankings/create`/`createMany` reject with 403 once `isSeasonEnded` — a third check deliberately separate from `isRankableNow` and `isBackfilled`. `isSeasonEnded` is **duplicated by hand** in `src/utils/episodeRankability.ts` and `backend/src/utils/episodeRankability.ts`. Frontend: `RankingComponent2.tsx` routes every not-yet-submitted column to `lockedEpisodeElements` once ended (same as `isBackfilled`/`isMissedDailyDay`) and `checkSubmitDisabled()` returns true; `RankingCountdown` shows "This season has ended — rankings are closed." / "Rankings close in …" and skips counting down to an episode whose window would only open after the end; `AdminEpisodes` disables Add for air times past the end. `POST /api/shows/updateSeason` only updates fields actually present in the body (`premiereDate`, `endDate`; `null` clears) — it used to do `premiereDate ?? null` unconditionally, which would wipe the premiere date whenever only `endDate` was sent.
- Prisma `migrate dev` (shadow-database mode) fails on this repo's real DB with `P1014` / `P3006` replaying the historical `20260709165605_rename_week_to_episode` migration (references a sequence, `Week_weekNumber_seq`, that a from-scratch shadow-db replay can't recreate cleanly) — this is pre-existing migration-history drift, unrelated to whatever schema change you're actually making, and the real dev DB itself is unaffected (`prisma migrate status` reports it as fully up to date). Don't try to fix/edit the old migration to work around it. Instead: hand-write the new migration's SQL into a new `prisma/migrations/<timestamp>_<name>/migration.sql` (matching Prisma's usual `-- AlterTable` / `ALTER TABLE ...` conventions, cross-check an existing migration file for the exact style) and apply it with `npx prisma migrate deploy` (from `backend/`), which applies pending migration files directly against the target DB and never spins up a shadow DB. Follow with `npm run prisma:generate` as usual.
- `GET /api/eliminations/` (`getEliminations()`) returns every elimination across *every* show/season the logged-in user has, grouped only by `episodeId` — it is not scoped to a season. Anything deriving "who's eliminated as of episode N" must filter to the current season first (see `currentSeasonEliminations` in `RankingComponent2.tsx`), otherwise episode-number collisions across shows (nearly every show has an "episode 1") leak the wrong show's contestants into a grid. **This is a different shape from `GET /api/eliminations/bySeason/:seasonId`** (`useEliminationsBySeason`): the unscoped endpoint groups by episode (`{episodeId, episodeNumber, seasonId, contestantIds: string[]}`), while the season-scoped one returns one row per elimination (`EliminationEntry`: `{id, episodeId, contestantId, eliminationType, episode}`). `ContestantDetailPanel` (and anything else built around per-contestant `eliminationType`) needs the latter — don't feed it the grouped shape.
- `RankingComponent2.tsx`'s "Rankings Table" / "By Contestant" tabs mirror `Insights.tsx`'s, but "By Contestant" reuses the *same* `ContestantDetailPanel`/`ContestantTrendChart` components fed synthetic `InsightsResponse` objects built from only the logged-in user's own `favoriteRankings`/`winnerRankings` (`buildOwnInsights` in `RankingComponent2.tsx`), not `useRankingsInsights` — the ranking page has no reason to show the season-wide average since it's not admin/analytics-facing, just the viewer's own submitted line. `averagePosition` there is just that single ranking's 1-indexed position (`contestantIds` index + 1), not an actual average.
- Eliminations are immutable at the bottom of the ranking column starting the *same* episode/day a contestant is eliminated (deliberate product decision, not a bug) — both `Episode.tsx` (live ranking) and `buildPastRankingColumn` (`src/utils/util.ts`, past rankings) compute one unconditional `getEliminationOrder(eliminations, episodeNumber)` threshold and use it both to exclude the contestant from the draggable/active list and to place them in the eliminated bucket. An earlier "lock in place" variant (contestant stays at their submitted rank position through their own elimination episode, only moving to the bottom starting the next one) was tried and explicitly reverted — don't reintroduce that split without being asked.
- `buildPastRankingColumn` (`src/utils/util.ts`) fills in any roster member missing from a past `Ranking.contestantIds` (e.g. historical data gaps) as an active fallback entry — but a contestant added to the season *after* a given episode already happened must not be backfilled into that episode's column, only into later ones. This is decided by comparing `Contestant.createdAt` to the episode's `airDate` (or, for DAILY shows, calendar day via `getTodayDayKey`) — see `wasContestantOnRosterFor` in `RankingComponent2.tsx`. The function takes two separate id lists for this reason: `seasonContestantIds` (full current roster, used only to pad every column to the same row count) and `eligibleContestantIds` (roster as of that episode, used for the active-fallback step) — don't collapse them back into one list.
- The ranking grid (`RankingComponent2.tsx` + `Episode.tsx`) and the insights table (`InsightsRankingTable.tsx`) both lay out contestant-by-episode data as one CSS Grid with `grid-auto-flow: column` and fixed-width columns — not a `<table>`. Two rules keep this from silently misaligning column-by-column:
  1. Every column must contribute the exact same number of grid cells; pad short columns with blank/null placeholder cells instead of returning a variable-length array (see `buildPastRankingColumn` in `src/utils/util.ts`).
  2. A column's cells must be direct children of the grid, never wrapped in a container div with an explicit `gridRow: span(...)` — a spanning wrapper stops a cell's real content height from growing its row's `1fr` track, so cells silently render smaller than the rank column.
- `.ranking-grid`'s `overflow-x: auto` (`RankingComponent.css`) only produces a real scrollbar if every ancestor between it and the viewport is actually width-constrained — on a narrow screen with enough episode columns to exceed the viewport, a single unconstrained ancestor anywhere in that chain lets the whole subtree shrink-wrap to the grid's full fixed-column width instead, which (since nothing in `index.css`/`App.css` sets `overflow-x` on `html`/`body`) widens the *entire page* rather than scrolling inside the grid — symptom is the navbar and everything else looking clipped with no way to scroll to the rest of the table. `.ranking-container` needs `max-width: 100%` (it's a non-stretched cross-axis flex item of `.rankings-main`, so without an explicit cap it has no ceiling) and `.ranking-panel` needs `min-width: 0` (it's a main-axis flex item of `.ranking-container`, where the default `min-width: auto` resolves to its fixed-column min-content size and overrides `max-width: 100%` unless explicitly zeroed) — both are required together, not just one. `Insights.tsx`'s equivalent `.insights-grid` doesn't need this: `.insights-panel` sits directly under `.insights-main` (already a firm `width: 100%` anchor) with no extra unconstrained wrapper in between, so its existing `max-width: 100%` already works as a cross-axis cap without needing `min-width: 0`.
- `InsightsRankingTable.tsx`'s `.insights-grid` used to have a bare trailing `1fr` column after AVG (`repeat(N+1, 2.5rem) 1.5rem 2.5rem 1fr`) meant to look like inert filler — it wasn't. `.insights-panel` was (at the time) `width: fit-content` with `align-items: stretch` — now a fixed full width, see the styling bullet below, but the same stretch-absorbing logic applies, and its sibling `.insights-tabs` (the Favorite/Winner pill row) has its own max-content width from its padded/bordered text labels; whichever of the two children is intrinsically wider sets the panel's resolved width, and `align-items: stretch` then forces *both* children — including `.insights-grid-wrapper`/`.insights-grid` — to that same width. With few episode columns the grid's own fixed-track sum is narrower than the tabs row, so the grid got stretched wider than its content, and since only that trailing `1fr` column could absorb the extra, it rendered as visible dead space to the right of the (sticky, `right:0`) AVG column instead of AVG sitting flush against the border. Fixed by dropping the trailing column and making the existing spacer column itself `minmax(1.5rem, 1fr)` — confirmed via a standalone Playwright/Chrome repro (see [[feedback_live_verification]] for the playwright-core + system Chrome setup) that this makes AVG's right edge exactly meet the grid's inner border with zero leftover, in both the "no stretch needed" and "tabs row wider than grid" cases. The `.insights-episode-title-overlay`'s `right: calc(1.5rem + 2.5rem + 5px)` still assumes a nominal 1.5rem spacer and doesn't grow with it, but since the spacer is blank filler this only ever costs the overlay a few extra px of harmless blank margin, never overlap with AVG — verified visually, not just computed.
- Ranking and Insights page styling (`RankingComponent.css`, `Episode.css`, `RankingCountdown.css`, `Insights.css`) share a light-card palette defined as `--rk-*` custom properties on `:root` in `src/index.css` (single purple accent `#7F77DD`, shared with Admin; card background is an *opaque* `rgb(201, 213, 231)` because sticky Rank/AVG cells must hide the columns scrolling under them — any tint on a sticky cell, e.g. `.insights-overall-cell`, has to be pre-composited to an opaque color too). Insights mirrors every Ranking-page rule below (1px grid border → `.insights-episode-title-overlay` offsets, spacing on `.insights-grid-wrapper` not the grid, `.insights-panel` fixed `width: 100%; max-width: min(100%, 60rem)` instead of `fit-content`, so the grid's `minmax(1.5rem, 1fr)` spacer absorbs spare width and AVG stays flush right). `.episode-title-overlay`'s `top`/`left`/`right` offsets track `.ranking-grid`'s border width (currently 1px) — change both together. Vertical spacing between the Favorite/Winner tabs and the grid must go on `.ranking-grid-wrapper`, never as `margin-top` on `.ranking-grid` itself: the overlay is absolutely positioned against the wrapper, so a grid margin silently pushes the header row out from under the "Episode" label. `Insights.css` defines several *global* classes that also exist in the ranking grid (e.g. `.rank-spacer`, cyan) and is loaded app-wide — ranking-page overrides for shared class names need a `.ranking-grid`-scoped selector to win. `ContestantIcon`'s own look (opaque `bg-gray-300` name strip over the photo's bottom edge, `mt-[-5px]` image offset) is deliberately left untouched here — a translucent label override was tried and reverted because it let the photo show through the name tag. `.ranking-container` is a fixed `width: 100%; max-width: min(100%, 60rem)` (matching `.ranking-top-bar`) with `.ranking-panel` as `flex: 1`, so the table always fills that width (spare room = the grid's trailing `1fr` column) instead of shrink-wrapping and re-centering when columns or the "X Episode N" chips change; `.active-episodes-container`'s `min-width` must stay equal to `.remove-button`'s width for the same reason. The active episode column's tint uses a separate `active-episode-column` class (on both its draggable and its eliminated cells) rather than `active-episode`, because `Episode.test.tsx` counts `.cell.active-episode` as "draggable cells".
- `RankingComponent2.tsx` scrolls `.ranking-grid` all the way right on load (`gridRef` + a `useEffect` doing `grid.scrollLeft = grid.scrollWidth`) so an overflowing grid defaults to showing the most recent episode/day column instead of episode 1 — a no-op when the grid isn't wide enough to overflow. That effect has to sit *above* the component's `if (loadingFlag) return` early return (all hooks do — same rule as the other `useEffect`s in this file), even though the grid itself is only mounted (and `gridRef.current` non-null) once `loadingFlag` is false and there's at least one contestant/episode; it depends on `[loadingFlag, currSeason?.id, rankableEpisodes.length, currSeason?.contestants?.length]` rather than firing on every render, and no-ops via a `gridRef.current` null-check on renders where the grid is replaced by one of the "no contestants/episodes yet" placeholders.
- Drag-and-drop ranking (`Episode.tsx`) uses `@dnd-kit/core` + `@dnd-kit/sortable`. `DndContext`/`SortableContext` render no DOM element of their own (pure context providers), so they can wrap grid cells without violating the "direct children" rule above.
- Contestant photos fall back to a naming convention when no `photoUrl` is set: `getImagePath` in `ContestantIcon.tsx` builds `/uploads/<show-slug>/season_<n>/contestants/<contestant-name>.png` and passes it through `backendUrl()` — same as the explicit-`photoUrl` case, both resolve to a backend-served URL, not a frontend asset import. Uploaded images are written to disk under `backend/uploads` (`uploadsDirectory = path.resolve(process.cwd(), "uploads")` in `backend/src/routes/images.ts` and `show.ts`, relying on `process.cwd()` being `backend/` in both dev and prod) and served statically at `/uploads` (`backend/src/server.ts`). The `/uploads` URL prefix is independent of where the directory physically lives — stored `photoUrl` values and the frontend's constructed paths only ever reference the URL, never the disk location, so the backing directory can be moved freely as long as `express.static()` and the two `uploadsDirectory` resolutions stay in sync and point at the same place.
- `AdminContestants.tsx` uses one card for both "Add contestant" and "Edit contestant" (`editingId` state, set by a list row's "Edit" button): the same dropzone, drag-and-drop and window-level paste listener supply either a new contestant's photo or a replacement one, and in edit mode the name is editable too (`updateContestant(id, { name?, photoUrl? })` → `PATCH /api/contestants/:id`, which accepts either field). Because the upload filename is derived from the contestant's name, a replacement photo is written to the *same* path as the old one — `uploadAction` therefore appends `?v=<timestamp>` to the returned path before it's stored as `photoUrl`, otherwise every `<img>` keeps showing the browser-cached old image after an edit. `express.static` ignores the query string and nothing parses `photoUrl` back into a disk path, so it's safe; don't strip it.
- `App.tsx` lazy-loads the three heavy pages (`Admin`, `RankingComponent2`, `Insights`) with `React.lazy` inside one `<Suspense fallback={<PageLoading />}>` around `<Routes>`, so each page (and recharts/dnd-kit) is a separate chunk instead of one >500 kB bundle that tripped Vite's chunk-size warning. Import a new full page the same way rather than statically. `Homepage`, `Navbar` and the modals stay static because they're needed on first paint.
- A contestant's icon label (`ContestantIcon`'s grey name strip) is their first name, computed by `getIconLabel(name, firstNameHasSpace)` in `src/utils/util.ts`: the first word of `Contestant.name`, or the first two words when `Contestant.firstNameHasSpace` is set (e.g. "Thien An Nguyen" → "THIEN AN"). Admins set the flag with the "First name has a space" toggle on the `AdminContestants` add/edit card, which also previews the label live. `ContestantIcon` doesn't take the flag as a prop. Every caller already passes `season`, so it looks the contestant up in `props.season.contestants` by `props.id`. A caller passing a season without a populated `contestants[]` (e.g. from the sparse `GET /api/shows/:showId`) would silently fall back to the one-word label. The photo filename fallback (`getImagePath`) still uses the full name and ignores the flag.
- `main.tsx` imports `bootstrap/dist/js/bootstrap.bundle.min.js` globally for side effects (this is what makes `data-bs-toggle`/`data-bs-target` work anywhere in the app, e.g. the Navbar's mobile hamburger collapse). If any component needs to drive Bootstrap's JS directly (e.g. `Navbar.tsx` calling `Collapse.getOrCreateInstance(...).hide()` to auto-collapse the mobile menu on nav-link click), it must import from that exact same file path — `import Bootstrap from "bootstrap/dist/js/bootstrap.bundle.min.js"; const { Collapse } = Bootstrap;` — never the bare `"bootstrap"` specifier. Vite/npm resolves the bare specifier to a different file (`bootstrap.esm.js`, per the package's `"module"` field) than the bundle `main.tsx` already loaded, creating a second, independent instance of Bootstrap's JS with its own document-level delegated click listeners for `[data-bs-toggle]`. Both instances fire on every toggler click, racing to mutate the same DOM node's classList — symptom is the toggle button working to open the menu but never reliably closing it again (each click re-opens it). `bootstrap.bundle.min.js` is a UMD build, so it only has a default export (the whole module), not named exports — destructure off the default rather than using `import { Collapse } from "..."` on that path.
- `buildOwnInsights` (`src/utils/util.ts`) builds an `InsightsResponse`-shaped object from a single user's own submitted `Ranking[]` — each ranking's submitted position becomes a synthetic `averagePosition` (not an actual average across users, despite the field name), letting the shared `InsightsRankingTable`/`ContestantDetailPanel`/`ContestantTrendChart` components render a "my submissions only" view without any prop-shape changes. `Insights.tsx`'s "All User Data"/"My Submissions" radio toggle (`dataScope` state) is the only caller — it swaps between this and the aggregated `useRankingsInsights` data feeding the same components. `RankingComponent2.tsx` no longer has an equivalent mode; instead it has a `ContestantSelect` dropdown (default "All Contestants") that dims (`ContestantIcon`'s `dimmed` prop, plain `opacity`) every other contestant's icon *only* in already-submitted past-ranking columns (`pastRankingsElements`) — deliberately not in the currently-open/active episode column (including its locked "eliminated this episode" cells), which has no `dimmed` wiring at all.
- `ContestantTrendChart` (Insights "By Contestant") draws a grey dashed "Number of Contestants" line (forced last in both the tooltip and the legend via `itemSorter` on each, since recharts sorts both by name by default) plus a shaded band below it, showing how many contestants were still in play at each episode (`getFieldSizeByEpisode` in that file: roster size minus distinct contestants eliminated at or before episode N, the same same-episode rule `getEliminationOrder` uses). It exists because submitted rankings only contain still-active contestants, so raw average ranks can't be compared across episodes: someone ranked last every week would otherwise look like they're climbing (10 → 9 → 8). The line and shaded area use `type="linear"` (the user prefers it over steps), so the boundary passes exactly through each episode's count. If steps are ever reintroduced, use the centered `type="step"`, not a one-sided variant. `stepBefore` draws the segment leading *into* episode N at N's value, which puts episode N−1's points below the boundary. `stepAfter` gives the final episode's level no width, so a last-placed contestant in the latest episode looks like they're above the shaded region (seen with DWTS S35, episode 3). Roster size is the season's current full roster, so a contestant added mid-season makes earlier episodes' boundary slightly too high (not adjusted via `Contestant.createdAt` yet). `EliminationEntry` now types the `episode?: { episodeNumber }` field the bySeason endpoint already returned.
- `POST /api/users/create` (`backend/src/routes/users.ts`) is a Prisma `upsert` keyed on email with `update: {}` — creating an account with an email that already exists silently returns the *existing* row (original password, original id) instead of erroring or updating the password. Reusing a test email across sessions to "reset" a test account's password will silently fail login with 401 instead of taking the new password — use a fresh/unique email (e.g. suffixed with a timestamp) for one-off test accounts instead.
- **Testing**: Vitest + React Testing Library, config lives in `vite.config.ts`'s `test` block (not a separate `vitest.config.ts`) plus `src/test/setup.ts`. Every component's test file is co-located beside it (`ComponentName.test.tsx` next to `ComponentName.tsx`), and every `.tsx`/`.test.tsx` pair gets its *own* folder — `src/components/` is one component-name folder per pair, with no exceptions for folders that used to group several related components together. `Admin/`, `Insights/`, and `modals/` are themselves just grouping folders one level up containing one such folder per component (e.g. `Admin/AdminShows/AdminShows.tsx` + `AdminShows.test.tsx`, `modals/LoginModal/LoginModal.tsx` + `LoginModal.test.tsx` + that modal's `Modal.css`) — don't add a new file as a sibling inside `Admin/`, `Insights/`, or `modals/` directly; give it its own subfolder like the others. When mocking a sibling-turned-cousin component in a test (e.g. `Admin.test.tsx` mocking `AdminShows`), the `vi.mock(...)` path must point at the new location (`../AdminShows/AdminShows`), not the old same-folder one (`./AdminShows`) — easy to miss since TypeScript won't catch a wrong string literal passed to `vi.mock`. `globals: true` is set in the Vitest config (so `describe`/`it`/`expect`/`vi` are ambient, no per-file import needed) — paired with `"vitest/globals"` in `tsconfig.app.json`'s `types` and `globals.vitest` merged into `eslint.config.js`'s `languageOptions.globals` so that doesn't trip `no-undef`. `eslint.config.js` also has a `**/*.test.{ts,tsx}` / `src/test/**` override disabling `@typescript-eslint/no-explicit-any`, since mocked query results and fixtures legitimately need it constantly — don't extend that override to non-test files. `src/test/setup.ts` polyfills `ResizeObserver` (Navbar's own height measurement, recharts' `ResponsiveContainer`), `IntersectionObserver` (react-tooltip via `@floating-ui/dom`), `window.matchMedia` (react-bootstrap `Dropdown`), and stubs `Element.prototype.getBoundingClientRect` to a fixed non-zero size — without that last one, recharts' `ResponsiveContainer` reads jsdom's always-zero rect on mount and permanently renders nothing but an empty wrapper div, since it treats zero-size as "wait for a real resize event" and jsdom never fires one. `src/test/renderWithProviders.tsx` is the shared test-utils wrapper (fresh Redux store + fresh `QueryClient` + `MemoryRouter`, with `preloadedState`/`route`/`routePath` options) — build `user` state for a test via its `preloadedState` option, not by seeding `localStorage` and hoping `userSlice.ts`'s module-import-time `checkUserLoggedIn()` call picks it up (that only runs once per test process, at first import, not per test). Mock data-fetching at the `utils/util.ts` function boundary (e.g. `vi.mock`/`vi.spyOn` on `getShows`, `addShow`, etc.) rather than mocking `hooks/queries.ts` itself, so real React Query cache/`isLoading` behavior stays under test. A `useMutation({ mutationFn: someUtilFn, ... })` that references the util function *directly* (rather than wrapping it in a local arrow function) gets called by React Query as `someUtilFn(variables, context)` — two arguments, not one — so a test asserting `expect(someUtilFn).toHaveBeenCalledWith(...)` needs a second `expect.anything()` arg to match; a mutationFn that's a local wrapper (e.g. `mutationFn: (id) => deleteX(id)`) only ever calls the wrapped function with the args the wrapper itself passes through. `@dnd-kit`'s pointer-sensor drag-and-drop (`Episode.tsx`) isn't covered by component tests — jsdom gives every element a zero-size `getBoundingClientRect` by default (before the stub above, which only fixes recharts, not dnd-kit's own internal collision math), so a real simulated drag has nothing meaningful to compute against; `Episode.test.tsx` only tests the activate/render surface, and `RankingComponent2.test.tsx` covers the reorder *callback* logic by invoking `onReorder`/`onActivate` directly against a mocked `EpisodeComponent`, bypassing dnd-kit's pipeline entirely.

- `Episode.tsx`'s `EpisodeComponent` is a fully controlled/presentational component (no internal `useState`, no `forwardRef`/`useImperativeHandle`) — `activeContestants` (the in-progress drag order) and `eliminatedContestants` are owned entirely by `RankingComponent2.tsx` and passed down as props, with `onReorder`/`onActivate` callbacks instead of local state mutation. This is deliberate: an earlier version kept `activeContestants` as local state seeded from `lastOrder` via a `useEffect` keyed on `[isActive]`, which reseeded (and silently discarded any in-progress drag order) every time `isActive` flipped from false back to true — which happened on every Favorite/Winner tab switch, since `activeEpisodes` used to be one `Set<string>` shared across both `RankType`s and got wiped on every switch. `RankingComponent2.tsx` now keeps `activeEpisodesByType`/`activeOrdersByType` as `Record<RankType, ...>` (one independent Set/order-map per type) specifically so switching tabs no longer touches the other type's active episodes or their drag order — only an explicit "X Episode N" removal (`removeActiveEpisode`) or a full show change clears anything. If you need to seed a newly-activated episode's order, do it in `activateEpisode` (guarded on "does this type already have a stored order for this episode" so re-activating after a tab switch doesn't reseed over real progress), not inside `EpisodeComponent`.
